# ERC-8060 consolidated strict no-admin reference — security and semantics review

**Review date:** 2026-11-19. Scope: [PR #6](https://github.com/ten-io-meta/erc8060-native-eth-value/pull/6), `contracts/ERC8060Reference.sol`. This is a **research reference implementation, not an audit certification**. No mainnet deployment or user deposit authorization is implied.

## Interface and architecture boundary

**Normative-looking, intentionally narrow interface:**
```solidity
interface IERC721Value {
    function valueOf(uint256 tokenId) external view returns (uint256);
    function burn(uint256 tokenId) external;
}
```
`type(IERC721Value).interfaceId == 0x88495fe7`. The independently supported historical `0xcadf338f` is a value-only discovery ID; it never proves holder burn/redemption semantics by itself. Generic methods do NOT include a mint price, commercial recipient, admin privileges, ERC-8098 supply limit, reservations, or TEN.IO references.

**Reference-only mint strategy:** the ownerless contract mints one ERC-721 to `msg.sender` for exactly the positive `msg.value`; issuance ID strictly increases; no supply cap. `_safeMint` requires any smart-contract recipient to support `onERC721Received`. The constructor sets ERC-721 name and symbol; neither value nor a fee recipient can be edited by a privileged role.

## Review of invariants and attack surfaces

| Property | Code path / mitigation | Residual caveat |
| --- | --- | --- |
| No issuer fee or authority | No `Ownable`, access controls, `withdraw*`, `pause`, setter, proxy upgrade, commercial pricing, treasury routing or TEN.IO dependency | No emergency admin rescue exists by design |
| Holder pays only own backing | `mint()` requires `msg.value > 0`; increases token `_redeemable[id]` and aggregate liabilities by precisely `msg.value` | Small dust values may be uneconomic to redeem after gas; frontend should warn |
| Correct redemption ownership | `burn(id)` verifies `ownerOf(id) == msg.sender` (not ERC-721 operator approval); returns the recorded wei value to the same caller | Contract wallets that reject ETH must transfer their token to a compatible wallet before redemption, if they can; not all wallet deployments permit recovery |
| Atomicity of payout | `_redeemable` removed, total debt decremented and ERC-721 burned before ETH `call`; failed ETH receipt reverts **all** state changes | This does not guarantee a contract-wallet owner can accept ETH |
| Reserve accounting | `totalRedeemableValue` increments at mint and decrements on successful burn; reserve deficit blocks burn; mint checks aggregate backing | Balances can contain unclaimable forced donations; `balance >= liabilities` is not a full external solvency audit |
| Reentrancy | `mint()` and `burn()` each have `nonReentrant`; tests cover `onERC721Received` and ETH payout callbacks | Ordinary ERC-721 transfer methods remain callable as designed; token custody can change independently |
| No cross-project coupling | `ERC-8098` is fungible ERC-20 policy; Reservable and OECL are separate optional research components; TEN.IO product fees/caps are elsewhere | ERC-165 interface support alone does not prove a third-party contract uses these exact guarded semantics |
| No surplus withdrawals | No fallback payable method or withdrawal | `selfdestruct`/forced deposits can strand ETH permanently; no admin can rescue it |
